# Product Discovery Methodology Rubric

*Daniel O'Rorke's rubric for judging whether a methodology can carry a
**gated** product discovery process end to end. Recorded here so every
methodology gets scored the same way; evaluations live alongside this file.*

## Scale

Each criterion gets one label — **Not well / Some support / Fully
supported** — and a **why**: the rationale must point at the methodology's
own tools, artifacts, or canon, not at a general impression. Where a score
is conditional, keep the single label and state the condition in the why.

## The 25 criteria

### Batch 1 — The problem

| # | Criterion |
|---|-----------|
| 1.1 | How clearly does it identify the people who will be affected? |
| 1.2 | How clearly does it identify the problem? |
| 1.3 | How well does it challenge that problem (to resolve XY problems)? |
| 1.4 | How well does it challenge our understanding (fight internal bias)? |
| 1.5 | Does it express the problem in a way that is easy to understand for stakeholders? |
| 1.6 | How well does it quantify the importance of the problem (range from WIBNI to contractually committed)? |
| 1.7 | How well does it quantify the confidence we have in the analysis? |
| 1.8 | Can it be applied to a wide variety of scenarios (regulatory, partners, VOIP)? |
| 1.9 | How well does it handle situations that are not directly **user**-based? |
| 1.10 | Does it provide clear decision criteria (go/no-go) based on understanding of the problem? |

### Batch 2 — The solution

| # | Criterion |
|---|-----------|
| 2.1 | How well does it allow us to explore multiple possible theoretical options? |
| 2.2 | Does it clearly identify a plausible set of solutions to the problem (within corp/business priorities)? |
| 2.3 | Does it provide a clear set of outcomes that will be delivered by the solution? |
| 2.4 | Does it identify a clear value proposition (why these outcomes matter)? |
| 2.5 | Can it be applied to a wide variety of scenarios (UX through detailed VOIP flows)? |
| 2.6 | Does it clearly identify effort involved in the proposed solution? |
| 2.7 | Does it provide clear decision criteria (go/no-go) based on the understanding of the **solution**? |

### Batch 3 — The market

| # | Criterion |
|---|-----------|
| 3.1 | Does it provide a clear way for resolving conflicting requirements? |
| 3.2 | Does it provide a clear way for picking the best solution for the market? |
| 3.3 | Does it clearly identify the size of the opportunity (expected revenue) including relevant constraints? |
| 3.4 | Does it provide simple/cheap ways to validate assumptions before implementation? |
| 3.5 | Does it clearly identify the positioning of this solution to the market? |
| 3.6 | Can it be applied to a wide variety of scenarios (SaaS to on-prem)? |
| 3.7 | Does it clearly identify a set of KPIs that will show whether this is a successful solution? |
| 3.8 | Does it provide clear decision criteria (go/no-go) given the market positioning of the solution? |

## Reading the rubric

- **WIBNI** = "Wouldn't It Be Nice If" — the speculative end of the
  importance scale; **contractually committed** is the hard end.
- Three criteria test **decision gating** at each stage (1.10, 2.7, 3.8);
  a methodology that never terminates will fail all three together.
- Three criteria test **breadth** (1.8, 2.5, 3.6) — regulatory/partner/VOIP,
  UX→deep technical, SaaS→on-prem — and expose where a method's core
  premise stops applying.
- Roll up by batch, not just in total: the **gradient** across problem →
  solution → market is usually the most informative finding.

## How to apply it

1. Score from the methodology's **published canon** (its own process guide,
   method cards, primary texts) and name the assets in each why.
2. Record **provenance and limits** at the top of the evaluation: which
   sources were read, which weren't available.
3. Note revisions with their reasons — a corrected criterion reading can
   change a score, and the record should show why.
4. Close with the verdict for a gated discovery process and, for this repo,
   which agents or method docs fill the gaps the methodology leaves.
